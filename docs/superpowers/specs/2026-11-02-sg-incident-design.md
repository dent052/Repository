# 設計: SG合格トレーナーを「事件対応」型に作り直す

2026-11-02 作成。ユーザーと合意した方向をまとめたもの。実装に入る前に `docs/design.md` をこの内容で書き直す。

## なぜ作り直すか

ユーザー本人が使ってみた感想:

- 用語が多すぎる。解説があっさりしていて頭に入らない。
- 問題を解く快感がなく、続かない。
- 解説を読んでも結局全部はわからず、覚えられない。
- やっていることは「情報の薄い参考書と問題集」。

最後に閉じた場面は「問題を解いている途中で解説を読み、そのまま閉じた」。

原因は、知識を「用語 → 一行の定義」というバラバラの単位で渡していること（例: 第2章はマルウェア11種の一覧表、解説は「〜はボット、〜はキーロガー」と用語を並べる）。覚える理由と用語どうしのつながりがないので、引っかかりなく流れていく。

一方、同じ作者のポケモン風の学習アプリ（FEマスター）は「まだやっていないが、あっちの方がやりたくなる」。物語の中で解く形が、開く理由になっている。

## 目的と前提

- **2026年12月の情報セキュリティマネジメント試験（現行制度）に合格すること。** 今日（11/2）から約5〜6週間。
- 学習時間は **通勤中15分＋寝る前15分、1日30分**。合計で18〜20時間ほど。
- スマートフォンで使う。通勤中は立ったまま片手で操作することがある。
- 作り直しに時間をかけすぎない。作っている間は勉強が止まるため、1週間以内に使える状態にする。

## 目標

1. アプリを開いたら、迷わず15分で終わる「1話」が始まる。
2. 解説を読んで終わらせない。間違えたら、同じ論点を別の角度から問う1問ですぐ取り返し、「わかった」で終わる。
3. 1話ごとに、手元に成果（わかるようになったこと、会社の安全度）が残る。
4. 過去問（IPA 公表問題）を軸に、出題される論点だけを扱う。

## しないこと

- 用語を網羅する体系テキスト（今の章1〜10の本文）は作らない、読ませない。
- 既存の作品（ポケモンなど）の世界観、キャラクター、名称は使わない。物語はオリジナルにする。
- 新制度（2027年度〜）への対応はしない。
- 後方互換・データ移行はしない（`CLAUDE.md` の方針）。古い進捗データは捨ててよい。

## 失敗とみなすもの（技術的に動いても）

- 1話が15分に収まらない、または途中で区切れず通勤の電車を降りるときに困る。
- 解説が今と同じく、用語を何個も並べて終わる。
- 物語が飾りになり、ただの問題集の前に文章が付いているだけに感じる。
- 片手で押しにくい（選択肢が小さい、スクロールしないと「次へ」がない）。

## 体験の形

### 世界観

- プレイヤーは架空の中堅企業に着任した、新任の情報セキュリティ担当者。
- 登場人物は少数に絞る（例: 上司のCISO、総務、システム部、委託先の担当）。名前・会社名・業種は実装者に任せる。
- 毎話「今日の事件」が起きる（不審メール、PC紛失、委託先からの漏えい、ランサムウェア、内部不正、監査の指摘など）。SGの出題範囲は職場で起きることそのものなので、事件と出題内容を一致させる。

### 1話（朝の通勤）

1. 事件の導入: 3〜5行。誰が・何に困っているか。
2. 問題 10問程度: その事件の論点に関係する問題を出す。過去問を優先し、足りない論点はオリジナルの本番レベル問題で補う。
   - 正解: 「被害を防いだ」演出。短く、すぐ次へ。
   - 不正解: 「被害が出た」演出 → **決め手の1文**（後述の `hook`）を表示 → 同じ論点の別の問題を1問すぐ出す（取り返し問題）。取り返し問題に正解したらその論点は「わかった」。同じ論点の問題がもうなければ出さない。
   - 解説の全文は「くわしく」を押したときだけ開く。
3. 結末: 事件の結果を1〜2行で書く。正答率で結末を変える（「被害ゼロで解決」／「一部被害が出たが収束」など2〜3段階）。
4. まとめ: 「今日わかるようになったこと」を最大3つ（その話で正解・取り返しに成功した論点の `hook`）。会社の安全度（＝合格予測点）の変化を表示する。

- 1問ごとに進捗を保存し、途中で閉じても次に開くと続きから始まる。
- 1話の問題数は、取り返し問題を含めて15分に収まる数にする（目安10問＋取り返し数問）。

### 寝る前（後始末）

- 間隔反復で今日が復習日になっている問題を出す（今の `box` の仕組みをそのまま使う）。物語上は「今日の事件の後始末」。
- 1回は最大15問程度で区切る。復習する問題がなければ、次の話に進める。

### 科目B

- 話数の後半（全体の後ろ3分の1程度）では、各話の最後に科目Bの事例問題を1問出す。
- 科目Bでは「決め手の1文を見つける」練習をする: 解答後、事例文の中で判断の根拠になる文を目立たせて表示する。解答前に文をタップして選ばせるかどうかは実装者の判断（片手操作で押しやすい場合のみ）。

### ホーム画面

- 大きなボタン1つ: 「次の話へ（第N話）」。寝る前の時間帯で復習がある場合は「後始末（M問）」を先に出す。どちらを出すかは時刻ではなく復習の有無で決めてもよい（実装者の判断）。
- 会社の安全度（合格予測点、600点が合格ライン）と、試験日までの残り日数。
- 事件ファイル: 解決した話の一覧。開くとその話で扱った論点の `hook` が読める（参考書代わりの最小の見直し）。
- 模擬試験（本番形式60問・120分）は試験前の確認用として残す。

## 話の数と順序

- 約30話。試験までの日数でちょうど終わる量にする（1日1話）。
- 順序は、配点が大きく基礎になるものから: 脅威・攻撃 → 認証・暗号 → 技術的対策 → リスクマネジメント・ISMS → インシデント対応 → 法務 → テクノロジ・マネジメント系 → 科目B中心の総まとめ。
- 過去問の章別の数（参考）: 章2:46, 章3:60, 章4:73, 章5:50, 章6:28, 章7:59, 章8:31, 章9:92, 章1:6, 科目B:12。オリジナル本番レベル: 科目A 401問、科目B 96問。
- 全問題を30話に入れる必要はない。1話10問×30話＝約300問＋取り返し問題が、使う量の目安。残りは取り返し問題・後始末・模擬試験に使う。

## データ

### 論点（新規）

各問題に「論点」を1つ付け、論点ごとに決め手の1文を持つ。これが解説の中心になる。

```js
// web/data/points.js
{
  id: "virus-worm-trojan",
  title: "ウイルス・ワーム・トロイの木馬",
  hook: "違いは「寄生するか・自分で増えるか」。寄生して増える＝ウイルス、単独で増える＝ワーム、増えずに正体を偽る＝トロイの木馬。",
}
```

- `hook` は1〜2文、80字程度まで。定義の羅列ではなく、**なぜそうなのか**、または**紛らわしい相手との違いは1つだけ**の形にする。
- 問題には `point: "<論点id>"` を付ける。取り返し問題は同じ `point` の問題から選ぶ。

### 話（新規）

```js
// web/data/episodes.js
{
  no: 1,
  title: "社長を名乗るメール",
  intro: "…",                 // 3〜5行
  questions: ["p-h30a-12", "a2-01", …], // 出す順
  b: "b-03",                  // 科目Bを出す話だけ
  endings: ["被害ゼロで解決…", "一部被害…", "…"], // 正答率の高い順
}
```

### 既存の問題

- 過去問・オリジナル本番レベル（科目A・科目B）はそのまま使う。各問に `point` を足す。
- 基礎レベル（`level: "basic"`）の問題、章の本文（`chapters.js`）、確認テスト、分野別演習は削除する。
- 用語集（タップで意味が出る機能）は、事件文・解説の中の分からない語を引くために残してよい。残すかどうかは実装者の判断。
- 科目Bの問題には、決め手の文を示す情報を足す（形式は実装者に任せる）。

### 進捗

- 今の `stats`（正誤・`box`・`due`）、`days`、`examDate`、`exams` を引き継ぐ。
- 新たに: どの話まで進んだか、途中の話の状態（何問目か、取り返し待ちか）、各話の結果（正答率）。
- 今の `passed`・`resume` は削除する。

## 決まっていること・既存から残すもの

- 構成・配信方法（`web/` の静的ファイル、1ファイル版、PWA、Artifact の db 保存）は今のまま。
- 間隔反復（box 0〜5、間隔 1/1/3/7/14/30日）、「自信なし」ボタン、合格予測の計算式、模擬試験はそのまま使う。
- 正解演出・不正解の揺れ、`prefers-reduced-motion` 対応、ダークモードは残す。

## 設計者が決めたこと（ユーザー未確認。読みながら確認してほしい点）

- **出す順序**: 仕組みと最初の7話（約1週間分）を先に使える状態にし、残りの話は学習の進みより先回りして週ごとに足す。データ検査は「存在する話はすべて整っている」ことを確かめ、30話そろっていることは前提にしない。
- **模擬試験**: 今のまま（オリジナル本番レベル問題から組む）。話で見た問題が出てもよい。過去問を軸にするので、話に入るオリジナル問題は少ない。
- **取り返し問題の選び方**: 同じ論点で、どの話にも入っていない問題を優先する。なければ、まだ解いていない後の話の問題も使ってよい。それもなければ、以前解いた問題を使う。
- **記録**: 取り返し問題の結果も stats（間隔反復）に入れる。結末と正答率は、話の本来の問題の1回目の正誤だけで決める。
- **1日に進める話数**: 制限しない。ホームに「今日の目安: 1話」と試験日までに終わるペースを表示するだけにする。

## 実装者に任せること

- 会社・登場人物の設定、各話の物語の文章。
- 各問題への論点の割り当てと、`hook` の文章（作業量が大きい。過去問とオリジナル本番レベル問題で数百問。論点は数は200前後を想定）。
- 演出の具体的な見た目（物語らしさは出すが、1問あたりの操作が遅くならないこと）。
- 試験日が未設定のときの話の割り当て（1日1話のまま）。

## 確認方法

- 1話を実際にスマートフォン幅で通して、15分以内に終わること、片手で押せることを確かめる。
- データの検査（`test/data.test.js`）: 全ての話の問題が存在する、全ての問題に `point` がある、全ての `point` に `hook` がある、`hook` が長すぎない、取り返し問題が選べる論点が十分ある。
